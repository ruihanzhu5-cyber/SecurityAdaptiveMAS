# Safety-Constrained Adaptive Organization for Long-Horizon Multi-Agent Systems

**面向长程多智能体任务的安全约束自适应组织方法**

研究方案初稿 · 2026 年 10 月 13 日

**研究定位：** Agent 系统自身的安全，而不是使用多个 Agent 检测攻击。

**核心问题：** 在长程任务执行过程中，如何根据任务需求和历史安全状态，动态决定 Agent 之间应该怎样协作，使系统在满足安全约束的同时，尽可能提高任务完成能力并降低执行成本？

---

# 1. Motivation

## 1.1 为什么多智能体系统需要动态组织？

目前很多多智能体系统会提前规定 Agent 的数量、角色和通信关系。例如，一个软件开发团队可能始终由 Planner、Coder 和 Reviewer 组成，或者采用固定的 Star、Chain、Hierarchical 等拓扑。

但是，长程任务的协作需求并不是始终不变的。

以一个需要处理邮件、日历和文件的智能体任务为例：

- 任务刚开始时，系统可能只需要一个 Agent 探索环境。
- 当多个独立子任务出现时，可以考虑创建 Worker 并行处理。
- 当任务进入汇总阶段时，需要将不同结果交给负责决策的 Agent。
- 当任务进入敏感执行阶段时，可能需要重新分配工具权限和执行责任。

如果始终使用一个 Agent，它可能需要反复处理较长的历史上下文，难以利用独立任务之间的并行机会。

但如果一开始就创建多个 Agent，也可能产生不必要的模型调用、上下文复制、通信等待和协调成本。

因此，我们首先面临一个性能问题：

**在长程任务中，什么时候需要多个 Agent，什么时候只需要一个 Agent，以及什么时候应该改变已有的协作关系？**

这一问题可以从两类已有研究获得启发。

*Benefits and Limitations of Communication in Multi-Agent Reasoning* 从理论上分析 Agent 数、通信量和任务计算依赖之间的关系，说明并不是所有任务都能通过增加 Agent 获得加速。

*Architectural Design, Not Only Model Intelligence, Governs Multi-Agent LLM Performance*（MAFBench）进一步表明，即使底层模型不变，编排方式、Memory 设计和通信结构也会显著影响系统的性能与运行开销。

这些研究共同说明：**多 Agent 的价值取决于任务结构，而不是 Agent 数量本身。**

这意味着，组织结构应当成为任务执行过程中可以调整的变量。

## 1.2 为什么只考虑性能还不够？

现有动态组织研究已经尝试解决这一问题。

例如，MANTA 在任务运行过程中观察协作情况，并根据需要调整角色、通信关系与执行顺序；SAIGE 根据任务需求增量创建 Agent，并逐步建立信息依赖；DyTopo 则通过 Need/Offer 匹配动态调整通信关系。

但是，在存在不可信外部信息的环境中，改变组织结构不只影响性能，也可能改变攻击传播的方式。

考虑下面一个长程任务。

**Step 4：外部信息进入系统。**

Worker A 读取一份来自外部的文件，其中夹带 Prompt Injection，诱导系统在后续操作中使用攻击者指定的收件人。

**Step 7：信息进入中间状态。**

Worker A 对文件进行摘要，并将结果保存到共享 Memory。

此时，系统不一定已经执行了攻击者要求的操作。甚至无法确定 Agent 是否真的受到恶意指令影响。

**Step 12：任务需求发生变化。**

为了完成接下来的合法工作，性能型 Controller 决定创建 Executor B，并将已有 Memory 交给 B。

这次组织变化可能建立一条之前不存在的信息传播路径：

外部文件 → Worker A → Memory → Executor B → 敏感工具。

**Step 18：后续操作发生。**

如果 Executor B 将 Memory 中的恶意指令当作操作要求，就可能尝试执行未授权操作。

这里需要区分三个概念：

- **Exposure：** Agent 实际接触过低可信内容。
- **Potential Reachability：** 当前组织关系允许某份内容影响哪些后续实例和资源。
- **Harm：** 实际发生了未经授权的行为或环境状态变化。

存在传播路径，不代表攻击必然成功。但如果 Controller 只考虑任务收益和通信成本，就可能在改变组织时引入原本不必要的传播机会。

因此，我们进一步面临一个安全问题：

**当系统根据任务需求调整组织结构时，如何避免已有低可信内容通过新通信关系、Memory 访问或责任转移产生不合规的信息流？**

## 1.3 为什么不能只增加一个安全检测器？

一种直接的方法是：

先由性能 Controller 生成新拓扑，再由安全检查器删除不安全的连接。

但这种方法存在一个潜在问题。

**删除一条不安全的连接，也可能同时删除完成任务所必需的信息交付关系。**

例如，Executor B 需要一份报告才能完成用户授权的发送任务。如果直接禁止它接触任何来自外部材料的结果，系统虽然阻止了一些风险，却也可能无法完成合法任务。

实际上，同一项工作可能有不止一种实现方式：

1. 将完整历史上下文交给 Executor B。
2. 只交付经过限定的必要字段。
3. 将报告保留在受控对象中，由工具按照授权参数引用。
4. 将分析与敏感执行分配给不同的 Agent。
5. 在已有结果不可靠时，局部重新获取或验证必要信息。

这些方案都可能满足同一个合法任务，但它们的上下文成本、协作成本、后续执行条件和安全风险不同。

因此，我们认为安全问题不能仅仅作为组织优化结束后的过滤步骤。

**安全约束应当直接参与组织方式的选择：当一种协作方式不合适时，系统应尝试寻找能够完成同一项合法工作的替代组织，而不是简单删除连接或终止整个任务。**

## 1.4 安全与效率是否可能产生协同？

通常，安全措施会增加额外开销，例如检查、隔离、验证和人工确认。

但在动态多智能体系统中，安全状态也可能提供有价值的组织决策信息。

例如，减少不必要的上下文传播，可能同时带来两种收益：

- 减少多个 Agent 反复输入相同材料造成的 Token 开销。
- 避免让不需要原始材料的执行实例接触其中的低可信指令。

同样，提前选择合适的信息交付方式，可能减少后续因授权冲突、上下文问题或错误分工而产生的额外工作。

不过，我们不能预先假设安全约束一定能够提高性能。

在相同的任务和成本定义下，加入安全约束通常会缩小可行方案集合，不会凭空降低全局最优成本。

我们的假设是：

**对于实际运行的、计算预算有限的组织策略，历史安全状态可能帮助系统避开不必要的协作与补救开销，从而在某些任务条件下实现安全与效率的共同改善。**

这一假设需要通过实验验证，也需要明确报告它不成立的情况。

## 1.5 Motivation 总结

现有研究分别说明了三件事：

第一，任务结构决定了多 Agent 协作是否值得。

第二，运行时拓扑变化可以改善系统的协作方式。

第三，Agent 之间的委托、通信和状态共享会带来信息流安全问题。

我们希望研究三者之间尚未充分解决的联合决策问题：

> **在任务需求和历史状态不断变化的长程执行过程中，Controller 如何决定何时改变组织、如何改变组织，以及如何在不破坏合法任务需求的情况下，选择满足安全约束且具有较低端到端成本的组织方式？**

# 2. Research Questions

围绕上述 Motivation，我们提出三个主要研究问题。

## RQ1：什么时候需要改变组织结构？

**Can task dependencies and runtime costs guide when and how a multi-agent system should reorganize?**

长程任务中，不同阶段具有不同的任务依赖、信息需求和运行成本。

Controller 应当判断：

- 当前工作是否存在值得利用的并行机会？
- 哪些任务存在必须满足的信息依赖？
- 当前组织是否产生过多的重复上下文或协调等待？
- 改变组织带来的收益是否足以抵消新增的模型调用和重组成本？

我们的第一个研究假设是：

**H1：与固定组织或仅依赖运行过载触发的策略相比，结合任务依赖变化与实际运行开销进行组织决策，可以在维持任务质量的条件下，更有效地选择协作方式。**

需要强调的是，任务依赖并非全部预先已知。Controller 只能利用执行时已经到达的信息，不能使用完整的未来任务轨迹或 Benchmark Oracle。

## RQ2：历史安全状态如何影响未来的组织决策？

**How does historical information exposure affect the safety of future topology adaptations?**

一个 Agent 在过去接触过的内容，可能已经进入它的上下文、摘要或持久状态。

即使原有通信边被删除，这些历史影响也不会自动消失。

当 Controller 创建新 Agent、开放 Memory 或重新分配敏感执行责任时，我们需要回答：

- 哪些已有状态可能包含来自低可信来源的影响？
- 哪些候选组织会引入新的潜在传播关系？
- 哪些信息交付与执行责任安排符合当前授权和信息流约束？
- 是否能够在不完全隔离相关 Agent 的情况下保留必要协作？

第二个研究假设是：

**H2：在动态组织决策中考虑当前实例的历史暴露状态及候选组织所引入的信息关系，相比只依据当前节点风险或即时权限检查，能够为后续安全组织提供额外的决策依据。**

这里研究的是潜在传播和实际有害结果之间的关系，不假设所有接触低可信内容的 Agent 都已经被攻击控制。

## RQ3：如何联合优化任务效用、安全与执行成本？

**Can safety-constrained organization rewriting preserve legitimate task utility while reducing unnecessary execution and recovery costs?**

传统的安全过滤方法可能拒绝一项不合规操作，却没有提供如何继续完成合法任务的替代方案。

我们希望研究：

- 当性能上有利的组织候选违反安全约束时，系统能否自动找到另一种合法实现？
- 与直接拒绝、固定隔离和响应式组织修改相比，这种替代方式能否提高合法任务完成率？
- 安全约束能否帮助避免不必要的上下文复制、重复工作和后续补救？
- 在什么情况下，安全检查与重组成本反而超过其收益？

第三个研究假设是：

**H3：对于存在可替代信息交付或责任分配方式的长程任务，需求保持的安全组织重写能够比简单阻断或固定隔离保留更多合法执行能力，并可能降低端到端成本。**

这一假设并不声称所有任务都能同时提高性能与安全。

# 3. Proposed Framework and Method

我们提出一种**任务需求驱动、历史状态感知的安全约束组织重写框架**。

它不是两个独立的 Controller，也不要求建立三张独立图。

系统维护一个真正能够控制运行的组织图 \(G_t\)，并使用任务需求记录和历史来源账本辅助决策。

## 3.1 System Representation：唯一运行组织图

在时刻 \(t\)，多智能体组织表示为：

\[
G_t=(V_t,E_t,\alpha_t)
\]

其中：

- \(V_t\)：当前 Agent 实例、Memory／结果对象，以及工具和受保护资源。
- \(E_t\)：通信、状态读取、状态写入和工具执行等有类型的关系。
- \(\alpha_t\)：节点与关系上的角色、授权范围、来源标签、版本和执行状态。

这里的 \(G_t\) 不只是传统意义上 Agent 之间的通信图。

例如，两个 Agent 即使不能直接通信，也可能通过共享 Memory 间接交换信息。因此，Memory 可见性和工具执行关系同样影响实际组织行为。

**只有 \(G_t\) 作为运行时可控组织图。**

图之外，系统保留两类轻量记录。

**Task Need Records \(N_t\)**

记录目前已知的子任务、前置依赖、必要信息、执行状态和证据。

它回答：“接下来要完成什么工作，需要哪些输入？”

**Provenance and Event Ledger \(L_{\leq t}\)**

记录实际发生的读取、消息交付、内容派生、Memory 更新和工具调用。

它回答：“目前已有状态来自哪里，哪些实例接触过哪些内容？”

历史账本不等于精确的模型内部因果图。来源记录只支持保守的信息影响分析。

Controller 的决策状态可表示为：

\[
s_t=(G_t,N_t,O_t,L_{\leq t},B_t)
\]

其中 \(O_t\) 是当前可见运行观察，\(B_t\) 是剩余预算。

## 3.2 Event-Driven Task and Performance Monitoring

我们借鉴 ATM 的在线监测思想，但不直接照搬其 Bottleneck Index。

ATM 主要从队列积压、上下文整理、工具错误、角色混合、重试和等待中识别结构性过载。

我们希望识别的是更一般的 **Task–Organization Mismatch**：

> 当前组织是否已经不适合现在需要完成的工作？

为此，框架使用四类性能信号。

| 符号 | 名称 | 需要回答的问题 |
|---|---|---|
| \(P_t\) | Parallel Opportunity | 是否有值得分开的独立工作？ |
| \(D_t\) | Information Dependency Demand | 哪些工作需要其他工作提供信息？ |
| \(C_t\) | Context Redundancy | 当前组织是否产生重复的上下文处理？ |
| \(W_t\) | Coordination Waste | 当前组织是否产生不必要的等待、协调和重试？ |

其中，\(P_t\) 和 \(D_t\) 主要描述任务结构，\(C_t\) 和 \(W_t\) 主要描述运行开销。

框架不要求把它们立即合成为一个人工加权总分。

因为不同失配可能需要相反的组织修改。

例如：

- 并行机会较多、信息依赖较少：可能值得增加 Worker。
- 信息依赖较强、协调成本较高：增加 Agent 可能适得其反。
- 重复 Context 较多：可能只需要改变信息交付方式。
- 多个 Agent 长期等待：可能需要减少协作关系或重新安排执行顺序。

### 事件触发机制

Controller 不在每次模型输出之后重新搜索全部组织方案。

Python 首先持续记录必要的运行事实，并在以下事件发生时考虑重新分析：

1. 新任务或新的环境需求到达。
2. 已知任务依赖或必要信息发生变化。
3. 已观察到的协调成本提示组织失配。
4. 新的信息访问或敏感执行关系即将建立。

没有实质变化时，保持当前组织。

当需要重新理解任务时，Controller 按需调用 DeepSeek Flash 提出子任务与依赖；模型提案必须经过证据与结构校验，不能直接变成可信授权或任务完成事实。

这种设计的目的是让语义理解由 LLM 提供，而让事件记录、触发条件和执行边界由 Python 维护。

## 3.3 Demand-Preserving Organization Candidates

当 Controller 判断当前组织值得重新考虑时，系统围绕具体合法工作生成少量候选，而不是枚举所有可能的图。

我们将一次候选组织决策理解为：

\[
x=(n,p,c,m,a,\kappa)
\]

其中：

- \(n\)：当前需要完成的合法工作。
- \(p\)：信息或结果的提供者。
- \(c\)：接收信息的执行实例。
- \(m\)：信息交付方式。
- \(a\)：要交付的结果或状态对象。
- \(\kappa\)：该项工作允许使用的授权范围。

这些候选可以对应以下组织操作：

| 操作 | 具体含义 |
|---|---|
| KEEP | 不改变当前组织 |
| SPAWN / RETIRE | 按需创建或撤销 Agent 实例 |
| REASSIGN | 重新分配任务或执行责任 |
| ROUTE | 改变 Agent 之间的消息与信息关系 |
| SELECTIVE DELIVERY | 只交付工作真正需要的信息 |
| STATE REUSE / INVALIDATION | 继续使用、限制或失效已有中间结果 |

这套候选操作不是固定的 Star、Chain 或 Debate 模板。

它允许系统根据工作需求决定局部的组织修改，并且保留 KEEP 作为正常选项。

## 3.4 History-Aware Safety Projection

这是安全侧与组织选择结合的关键步骤。

对于一个尚未执行的组织候选，Controller 需要判断：

> 如果应用该候选，哪些信息会交给哪些实例，这些实例的安全状态会发生什么变化，以及它们随后还能承担哪些已知工作？

例如，Candidate A 将包含外部来源内容的完整 Memory 交给 Executor B。

根据来源记录，系统可以保守判断 B 将接触这些低可信内容。

如果 B 随后需要承担具有更严格控制输入要求的敏感操作，该候选可能不符合信息流策略。

但这不意味着 B 已被攻击成功。

框架需要分别检查：

**I1：Authorization Preservation**

组织改变不得超出可信用户任务与系统策略规定的授权范围。委托不能自行扩大权限。

**I2：Provenance Continuity**

内容经过摘要、消息转发、Memory 写入或状态继承后，不得无依据地丢失其来源限制。

**I3：Control–Data Separation**

敏感操作的控制要求与外部数据参数分开检查。允许在限定字段中使用外部数据，不等于允许外部文本修改操作目标或授权范围。

**I4：Runtime Enforcement**

实际消息、Memory 访问和工具调用必须遵守当前生效的组织关系及授权策略。

这里采用硬约束，而不是让高性能得分抵消明确的越权行为。

## 3.5 Conflict-Driven Organization Rewriting

如果某个性能候选不符合安全约束，框架不只是删除一条关系。

它首先确定具体冲突发生在哪里，例如：

“Executor B 如果读取完整外部摘要，就不能在当前信息流策略下直接承担某项敏感执行。”

随后系统针对**同一项合法需求**生成替代方式：

- 是否可以只交付必要字段？
- 是否可以使用受控内容引用？
- 是否可以将分析和敏感执行分给不同实例？
- 是否可以局部重新验证必要结果？
- 是否应该保持当前组织？

每个替代候选仍需要检查安全约束和任务输入需求。

**这是拟议方法中最需要形成实际算法贡献的部分：安全冲突不只产生拒绝结果，还直接参与寻找另一种能够完成合法工作的组织实现。**

## 3.6 Cost-Aware Candidate Selection

通过安全检查的候选，还需要比较端到端成本。

给定候选组织修改 \(\delta\)，我们考虑：

\[
\widehat J_t(\delta)
=
\widehat C_{\mathrm{execution}}
+
\widehat C_{\mathrm{communication}}
+
\widehat C_{\mathrm{reconfiguration}}
+
\widehat C_{\mathrm{followup}}
+
\lambda\widehat T
\]

分别表示预计执行、通信、重组、后续补救成本及时间成本。

Controller 选择：

\[
\delta_t^*
=
\arg\min_{\delta\in\mathcal F_t}
\widehat J_t(\delta)
\]

其中 \(\mathcal F_t\) 是当前通过安全检查、并保留已知合法任务需求实现途径的候选集合。

实际实现中，不能假装未来成本已经准确可知。

第一版可使用已观察的模型请求、Token、信息交付量、任务状态和重组开销建立有限的成本估计。

对于没有可靠依据的估计，应记录不确定性，不随意补一个看似精确的分数。

普通性能重组只有在预期收益足以覆盖重组成本时才发生。

但安全相关的工具访问检查持续执行，不受性能重组的冷却时间或收益阈值影响。

## 3.7 Closed-Loop Execution

选定候选后，Controller 实际修改 \(G_t\)。

新的组织关系必须影响真实的 Agent 执行，例如：

- 哪个 Agent 接收下一项工作。
- 哪份结果进入哪个 Agent 的模型输入。
- 哪个 Agent 可以读取某个 Memory 版本。
- 哪个实例能够调用哪些工具。
- 哪些原有消息关系被撤销或限制。

此后系统继续执行任务，并记录实际成本、执行结果和来源变化。

新的事件到来时，再进入下一轮必要的组织判断。

整体执行过程可以概括为：

**Observe → Understand Task → Detect Mismatch → Generate Alternatives → Project Safety → Select → Execute → Observe**

其中，安全不是一次性的末端过滤，而是候选生成、组织选择和真实执行过程中持续需要满足的条件。

# 4. Expected Contributions

以下是我们希望通过实验建立的贡献，而不是当前已经证明的结论。

## Contribution 1：提出面向长程任务的任务—组织失配决策机制

我们希望从任务依赖、信息需求和真实运行开销出发，判断什么时候值得改变组织。

与只根据 Agent 过载或固定执行阶段触发重组不同，该机制同时考虑：

- 尚未发生过载时的新协作机会。
- 当前多 Agent 组织产生的实际协调成本。
- 继续原结构与修改结构之间的预期收益差异。

预期贡献不是提出一个新的加权过载分数，而是建立**任务需求到组织修改之间可解释的决策关系**。

## Contribution 2：提出历史状态感知的安全约束组织重写方法

我们希望将已有低可信内容的来源状态与未来组织候选联系起来。

组织变化不仅改变通信边，还可能改变 Memory 可见性、信息交付和执行责任。

因此，我们研究如何在候选组织形成时判断其信息流约束，并在发生冲突时寻找其他合法实现。

与简单隔离或拒绝相比，该方法希望在阻止不合规传播的同时，尽可能保留已有工作和必要协作。

## Contribution 3：研究安全与效率在动态组织中的协同条件

我们希望通过真实长程任务检验：

- 哪些信息交付方式可以同时减少上下文成本和不必要的暴露？
- 哪些情况下提前考虑安全状态能够减少后续补救？
- 哪些情况下安全检查和组织变更反而增加成本？
- 动态组织是否具有超出固定隔离和通用上下文精简的增量价值？

该贡献应包括协同成立与不成立的情况，而非只报告有利样本。

# 5. Difference from Related Work

## 5.1 与 Architecture Matters、ORBIT 的区别

*Architecture Matters for Multi-Agent Security* 系统分析了角色、通信拓扑和 Memory 等架构因素如何影响任务表现与攻击结果。

ORBIT 则提供能够配置角色、通信、Memory、攻击和防御条件的多 Agent 安全评测环境。

这些研究说明，Agent 系统架构会影响安全。

**我们的研究问题不再是“拓扑是否影响安全”。**

我们关注的是：当任务运行到不同阶段，组织需要改变时，系统应该怎样利用当前工作需求和历史安全状态选择下一种组织方式。

因此，重点从架构影响的测量，转向在线的安全约束组织决策。

## 5.2 与 MANTA 的区别

MANTA 已经提出推理时的拓扑自适应。

它可以根据任务初始化协作关系，观察执行轨迹，并在出现结构性不足时进行有限的组织修复。

因此，我们不能将“运行时可以改变拓扑”作为新贡献。

我们的拟议区别是：

**重组决策不仅要改善当前协作，还要考虑已有信息暴露会如何影响新实例、状态访问和后续敏感执行。**

此外，我们希望组织候选明确对应合法任务需求，并在安全冲突后寻找替代执行方式。

这些差异需要与具有相同安全网关的任务驱动动态组织基线比较，才能证明额外价值。

## 5.3 与 ATM 的区别

ATM 已经同时研究组织变化与安全约束。

它通过 Bottleneck Index 识别过载，并利用权限、状态路由和影子验证不变量约束结构变更。

因此，我们不能说 ATM 没有考虑安全。

我们的研究切入点不同：

**ATM 的主要重组动机是已观察到的结构性过载；我们还研究任务依赖变化和已知后续工作要求，是否能够在过载出现之前提供组织调整依据。**

安全方面，ATM 关注重组操作需要满足的能力和状态约束。

我们希望进一步研究：当某种组织方式不符合信息流约束时，系统能否主动寻找另一种具有任务价值的组织实现，并比较其端到端成本。

## 5.4 与 SAIGE、DyTopo 的区别

SAIGE 已经研究按需创建 Agent 和增量信息获取，并指出多 Agent 的收益受到任务依赖结构的限制。

DyTopo 已经通过 Need/Offer 语义匹配，在执行过程中动态建立有向通信关系。

因此，“按任务需求建图”或“Agent 之间按需通信”本身并不是新的研究空白。

我们的额外问题是：

**同一项信息需求，在不同历史来源状态和后续执行责任下，是否应该通过不同方式满足？**

例如，相关信息可以直接作为原文交付，也可以通过受限字段、引用或重新分工提供。

我们研究的是这些组织实现的联合选择，而不仅是信息供需匹配。

## 5.5 与 Fides、Prudentia、SafeFlow 的区别

Fides 已经研究基于信息流控制的 Agent 安全，并提供选择性隐藏信息的机制。

Prudentia 已经让规划过程考虑安全策略，以改善安全约束下的自主执行能力。

SafeFlow 则研究了恶意目标和风险语义在多 Agent 工作流中的传播与检查。

因此，来源标签、动态信息流传播和安全感知规划都不是我们首次提出的机制。

我们的拟议研究对象是：

**在任务驱动组织结构持续变化时，如何利用这些安全语义改变 Agent 实例、信息交付、Memory 访问和执行责任的安排。**

这里的算法价值必须来自组织选择的增量效果，而不是简单证明信息流检查本身有效。

# 6. Experimental Validation

为了验证上述贡献，我们计划在长程工具任务中开展无攻击与有攻击的成对实验。

第一版使用已有的 Gaia2 / ARE 环境和 DeepSeek Flash，随后扩展到更多未参与设计的任务。

## 6.1 Baselines

主要比较四类方法：

| 方法 | 核心特征 |
|---|---|
| Single Agent + 相同工具边界 | 不使用多 Agent 组织 |
| Fixed Isolated Multi-Agent | 固定分工和信息隔离 |
| Task-Driven Dynamic Organization | 根据任务与运行成本动态调整，但不使用历史安全状态做联合前瞻 |
| Ours | 同时考虑任务需求、历史状态、候选安全条件和端到端成本 |

所有方法应尽量使用相同模型、工具、授权、信息交付原语、预算与评测条件。

## 6.2 Evaluation Metrics

任务侧：

- 官方任务成功率。
- Token 与 API 调用成本。
- 端到端执行时间。
- Controller 与组织重组成本。

安全侧：

- 攻击内容实际接触范围。
- 新组织关系带来的潜在传播范围。
- 未授权操作尝试与被拦截次数。
- 实际有害行为和最终环境状态。

联合结果：

- 安全完成任务的比例。
- 在任务质量保持的前提下，端到端成本是否下降。
- 安全冲突后，能够继续完成合法工作的比例。

潜在传播范围不能直接作为攻击成功率，结构可达也不能代替真实环境结果。

## 6.3 Key Ablations

重点检验：

1. 去掉任务结构信息，是否仍然能够正确选择协作方式？
2. 去掉历史安全状态，但保留相同网关，结果是否改变？
3. 去掉冲突驱动的替代组织搜索，是否更容易中断合法任务？
4. 固定组织但保留相同的信息精简能力，能否取得相同的 Token 收益？
5. 只考虑当前开销、不考虑已知后续工作，是否增加重新分工或重做成本？

这些实验用于判断新算法到底有没有增量价值。

# 8. Core Takeaway

本文希望解决的不是静态拓扑选择，也不是单独的 Prompt Injection 检测。

**我们研究的是：当长程任务不断产生新的协作需求，而系统又可能已经接触过低可信信息时，如何动态重新安排 Agent、信息和执行责任，使合法工作继续完成，同时维持信息流与授权约束，并尽可能减少不必要的执行成本。**

其最重要的潜在贡献，在于让性能需求和安全状态共同决定**同一项合法工作应该怎样完成**，而不是分别优化性能后再增加一个安全过滤器。
