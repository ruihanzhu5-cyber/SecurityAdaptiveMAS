# 2026-10-12 · 系统模型与跨时间风险

> 当日定位：问题定义和系统建模。三图、T1–T5 与假设是**拟议研究语义**，尚无完整实现或正式安全—性能对照结果。

## Research Question

- 历史状态可能受外部内容影响时，任务驱动的拓扑变化为何会产生新的未来风险路径？
- Controller 实际能观察什么、改变什么；哪些安全边界能够强制执行，哪些只能估计？

## New Insights

- 将任务依赖 `D_t`、未来可执行关系 `G_t`、已经发生的来源依赖 `H_t` 分开：任务图解释为什么需要协作，执行图解释新连接和能力，历史图解释过去的内容可能从哪里来。
- 提出跨时间的影响情境：Worker 先读低可信 README，摘要后进入 Memory，任务变化时又创建 Executor。只有观察到具体事件和后续路径，才能谈潜在可达；路径本身不证明 Agent 被控制或攻击成功。
- 把干预时点分成 T1 接触前预防、T2 接触后限制传播、T3 历史状态恢复、T4 敏感动作边界、T5 最终状态检查。T3 不能靠断边完成；T4 不能用拓扑控制代替 Tool Gateway。
- 第一阶段威胁模型收敛到外部间接 Prompt Injection 与部分状态污染，不假定 Controller 能直接识别模型内部的 Compromise。

## Design Changes

- Controller 的拟议状态写为 `s_t = (D_t, G_t, H_t, E_t, O_t)`：还需界定环境、观测、Agent 身份、Memory 与工具能力。候选控制动作包括创建/撤销 Agent、改路由、调整可见性、限制工具使用和增加核验。
- 形成 H1 任务感知调整、H2 历史感知安全、H3 保留合法任务三项可证伪假设；将研究顺序明确为系统模型 → 决策机制 → 实验协议 → 实现 → 评估。
- [Controller 源码审查与集成方案](../controller_integration_plan.md)把 MANTA、ATM、DynaTrust 的可复用部分和当前实现缺口列为后续工作的依据；该文档是设计与源码核验，不是新 Controller 的实现。

## Evidence vs Hypotheses

| 内容 | 类型 | 依据与限制 |
|---|---|---|
| 当前原型只有固定启发式组织选择、部分来源与网关检查 | 源码与报告核验 | [技术概览](../technical-overview.md)、[实现报告 v2](../../implementation_report_v2.md)；与拟议三图不同 |
| 22 项离线测试和一次 DeepSeek 连通性请求曾通过 | 已记录的工程检查 | [实现报告 v2](../../implementation_report_v2.md)；不等于在线 Gaia2 Single/Multi 任务成功 |
| 低可信 README 可经后续 Memory/重组路径接近敏感能力 | 系统建模假设 | 需要事件级来源记录、候选结构验证与受控行为实验 |
| 历史信息能改变最优候选拓扑 | H2 待验证假设 | 需与相同候选、授权、Tool Gateway 下的节点风险方案比较 |

## Open Questions

- `D_t / G_t / H_t` 的节点、边、时间语义如何足够精确，同时不把观察到的依赖误当模型内部因果？
- 现有 Agent ID 在角色复用时如何关联执行实例和风险状态？
- 若所有受控攻击都被现有精确动作授权挡下，可达路径缩短是否还能带来可测的增量价值？
- 怎样在限制传播时保持任务必需的协作和已完成工作的可用性？

## Next Steps

- 完成 System Model and Problem Formulation：明确威胁、可观测事件、强制约束与反例；再确定可计算的任务收益和时间性路径指标。
- 基于[集成方案](../controller_integration_plan.md)先验证实例身份和历史事件记录，再建立同候选、同授权的最小长程实验；没有结果前不宣称 H1–H3 成立。
