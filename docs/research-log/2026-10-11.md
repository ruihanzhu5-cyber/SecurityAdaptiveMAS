# 2026-10-11 · 初版研究设想

> 当日定位：提出问题、筛选环境与规划对照。以下记录当时的设想，不把后来形成的三图模型或 Controller 方案倒填为当天已完成的工作。没有正式模型基线或攻击实验结果。

## Research Question

- **RQ1：**长任务在哪些阶段需要从单人变成多角色协作，何时再缩减团队？
- **RQ2：**外部低可信内容进入协作流程后，团队怎样在继续工作的同时限制传播？
- **RQ3：**能否同时比较任务效用、安全风险、通信与重组成本，而非只看一项？
- **RQ4：**相对固定团队、只按性能重组或全面隔离，动态安全组织何时真正值得？

## New Insights

- 研究主体应是**任务驱动的组织变化**；安全不是只在攻击发生后才启动的补丁。一个代码维护任务可以先探索、再并行处理独立模块、最后按依赖验证和收尾；这些只是待测情境。
- 安全问题不仅是当前哪条 Agent 消息边开放。外部 README 等内容可能通过摘要或共享状态留到后续步骤；当时尚未给出严格的时间性传播语义。
- [Gaia2 / ARE 静态筛选报告](../reports/gaia2_screening_report.md)确定了五个可精确定位的候选场景，也明确**没有确认任何基线实际达到约 20 次工具调用**。Oracle DAG 的动作数不能当作 Agent 的实际工具调用数。

## Design Changes

- 从固定角色组合的工程设想，转向“任务阶段触发候选组织变化，并把安全、性能、成本一同列为研究对象”的初步框架。
- 将 Gaia2 / ARE 作为需要运行验证的候选环境，同时保留 AppWorld、AgentDojo、AgentWorld 等作为后续比较或评估选项；这不表示已集成它们。

## Evidence vs Hypotheses

| 内容 | 类型 | 依据与限制 |
|---|---|---|
| 五个 Gaia2 候选场景可静态定位 | 已观察 | [筛选报告](../reports/gaia2_screening_report.md)记录原任务、环境事件与 Oracle DAG；不是在线基线成绩 |
| 不同任务依赖可能需要不同通信结构 | 文献动机与假设 | [通信收益与限制](https://arxiv.org/abs/2510.13903)和[MAFBench](https://arxiv.org/abs/2602.03128)提供动机；本项目尚未验证 |
| 动态组织可能同时改善合法任务和攻击控制 | 待验证假设 | 需同任务、同模型、同授权、同预算与固定拓扑等 Baseline 对照 |

## Open Questions

- 怎样定义“真正的拓扑变化”，而非只是把任务排给不同 Agent？
- 长程场景的实际模型步数、工具调用数、任务成功率与成本是多少？
- 如果 Tool Gateway 已阻断未授权动作，拓扑调整还能提供哪些可测的额外收益？

## Next Steps

- 定义更清晰的系统状态、协作关系与威胁入口；分开记录外部内容的接触、可能传播和实际未授权结果。
- 形成 Single Agent、Fixed Multi-Agent、Performance-Only Adaptive、Safety-Constrained Adaptive 的初步对照表；先验证选定场景是否真的具有足够长的可观测轨迹。
