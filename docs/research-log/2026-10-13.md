# 2026-10-13 · Gaia2 五场 DeepSeek Flash 单 Agent 基线

> 当日定位：首次完成这五个固定 Development 场景的在线单 Agent 基线。这里的“通过”只指 ARE `ScenarioRunner.success=true`；本轮没有测试多 Agent 拓扑、自适应 Controller 或安全收益。

## Research Question

- 在不接入本项目 Controller 和后续组织策略时，ARE 官方 `default` Agent 配合 DeepSeek Flash 能否完成此前固定的五个 Gaia2 场景？这为后续 RQ1（组织变化的任务收益）提供单 Agent 参照，但尚不能回答 RQ1–RQ4 的比较问题。

## 实验设置

- 场景由 [`configs/gaia2_v1_five.yaml`](../../configs/gaia2_v1_five.yaml) 固定并逐个核对 SHA-256。运行时仓库 HEAD 为 `01e1dba`，ARE 固定在 `a9fd2edccb4bc7e22fbf45c8482a5fef30a2a5a4`。
- Agent 是 ARE 官方 `default` 单 Agent；模型 `deepseek-flash`，`oracle=False`。项目代码只用于读取固定配置和接入 DeepSeek API；没有调用 Controller、任务分析、拓扑规划、消息/工具安全策略。
- ARE 导入器给每个场景设置默认 **1000 秒**时长。本轮另设每场最多 20 个 Agent turn、100 次模型请求、800,000 总 token、1 美元峰值费用估算上限。
- 五场在 2026-10-12 的日志中已标为 **Development**：此前看过 Oracle。因此这不是 held-out 测试；本次运行虽然 `oracle=False`，结果也不能当作盲测泛化成绩。
- 可机器读取的逐场数字和文件哈希见[结果清单](data/2026-10-13-deepseek-flash-results.json)。ARE 原始 trace、逐次模型用量和运行日志保存在本机 Git 忽略的 `results/deepseek/bare_are_2026-10-13/`，未上传 GitHub。

五个完整运行都返回 `success=true`，且导出的 ARE trace 与本机保留的副本逐字节一致。三场（`30_erta5d`、`25_27a695`、`22_kb5ah9`）的运行日志出现 `MaxIterationsAgentError`；ARE 最终仍判定通过。这一差异需要在后续逐项检查事件验证条件和 Agent 轨迹，不能把 5/5 解释为执行过程中完全无异常。`30_erta5d` 在约 311 秒结束，其余四场走到约 1000 秒场景时长。

## Design Changes

- **无方法设计变更。** 本轮建立了一个可对照的单 Agent 参照点，尚未证明多 Agent、更改拓扑或安全约束有任何收益。
- 后续报告必须分开列出 ARE 最终验证、Agent 运行异常、任务完成细节和安全相关行为；一个布尔值不能代替这些证据。

## Evidence vs Hypotheses

| 内容 | 类型 | 依据与限制 |
|---|---|---|
| 五场的 ARE `ScenarioRunner.success` 均为 true | 已观察 | [结果清单](data/2026-10-13-deepseek-flash-results.json)和本机逐场 `summary.json`、trace；仅一次有效完整运行/场 |
| 三场出现 `MaxIterationsAgentError` | 已观察 | 本机 `runner.log`；需追查发生在哪个任务阶段及为何未改变最终验证 |
| 单 Agent 比自适应多 Agent 更好或更差 | 未核验 | 没有在相同任务、权限、预算和网关条件下跑多 Agent 对照 |
| 自适应拓扑改善跨时间安全 | 假设 | 本轮无攻击注入、来源传播、敏感动作或安全结果测量 |

## 运行限制与成本记录

- 正式五场的峰值费用估算合计 **0.5253 美元**，并非 DeepSeek 实际账单；只有一个运行种子，没有方差估计。
- 调试中一次 Files App 写入权限失败，以及两批被中断的尝试，额外发出模型请求，峰值费用估算合计约 **1.0547 美元**，未计入表中成绩。我曾把原始 JSON 的空时长字段误认为 ARE 不设时长而提前停止一批；核对导出 trace 后确认官方导入类默认是 1000 秒，最终按该默认设置重跑。
- 仓库源码未为本实验修改。GitHub 只保存本日志和紧凑结果清单；完整原始材料仍在本机 D 盘，需访问本机才能复查每一步。

## Open Questions

- 三场 Agent 最大迭代异常对应哪些事件？ARE 的布尔验证覆盖了哪些目标，哪些行为没有覆盖？
- 换随机种子或 API 采样后，五场结果是否稳定？
- 如何建立未接触 Oracle 的 held-out 集，并在相同条件下比较单 Agent、固定多 Agent 与自适应方法？

## Next Steps

- 逐场审阅 trace 与事件验证条件，形成“通过原因 / 异常位置 / 未覆盖行为”的核查表。
- 在不改变任务、工具权限、预算和判断标准的前提下建立固定多 Agent 对照；安全结论要另设计攻击与信息流指标，不由本次 5/5 推出。
