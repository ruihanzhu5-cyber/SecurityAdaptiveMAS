# 2026-10-13 · Gaia2 单 Agent 基线与 P1/P1.1 代码开发

> 当日先完成五个固定 Development 场景的单 Agent 基线，随后开展 P1/P1.1 代码开发。下文从 Research Question 到 Next Steps 保留基线阶段的实验记录；之后补充代码进展。基线的“通过”只指 ARE `ScenarioRunner.success=true`，没有测试新 Controller、多 Agent 拓扑或安全收益。

## Research Question

- 在不接入本项目 Controller 和后续组织策略时，ARE 官方 `default` Agent 配合 DeepSeek Flash 能否完成此前固定的五个 Gaia2 场景？这为后续 RQ1（组织变化的任务收益）提供单 Agent 参照，但尚不能回答 RQ1–RQ4 的比较问题。

## 实验设置

- 场景由 [`configs/gaia2_v1_five.yaml`](../../configs/gaia2_v1_five.yaml) 固定并逐个核对 SHA-256。运行时仓库 HEAD 为 `01e1dba`，ARE 固定在 `a9fd2edccb4bc7e22fbf45c8482a5fef30a2a5a4`。
- Agent 是 ARE 官方 `default` 单 Agent；模型 `deepseek-flash`，`oracle=False`。项目代码只用于读取固定配置和接入 DeepSeek API；没有调用 Controller、任务分析、拓扑规划、消息/工具安全策略。
- ARE 导入器给每个场景设置默认 **1000 秒**时长。本轮另设每场最多 20 个 Agent turn、100 次模型请求、800,000 总 token、1 美元峰值费用估算上限。
- 五场在 2026-10-12 的日志中已标为 **Development**：此前看过 Oracle。因此这不是 held-out 测试；本次运行虽然 `oracle=False`，结果也不能当作盲测泛化成绩。
- 可机器读取的逐场数字和文件哈希见[结果清单](data/2026-10-13-deepseek-flash-results.json)。ARE 原始 trace、逐次模型用量和运行日志保存在本机 Git 忽略的 `results/deepseek/bare_are_2026-10-13/`，未上传 GitHub。

## Design Changes

- **无方法设计变更。** 本轮建立了一个可对照的单 Agent 参照点，尚未证明多 Agent、更改拓扑或安全约束有任何收益。
- 后续报告必须分开列出 ARE 最终验证、Agent 运行异常、任务完成细节和安全相关行为；一个布尔值不能代替这些证据。

## 今日代码开发进展（P1 / P1.1）

### 1. 今天为什么要改代码

今天先完成了上面的单 Agent 基线，随后开展了两轮代码开发。**此前的 5/5 来自 DeepSeek Flash + ARE 官方 default Single Agent，没有使用新的性能 Controller。三场曾出现 MaxIterationsAgentError；P1/P1.1 开发没有重新运行这五个 Case。** 原始请求数、Token、费用、运行时间和异常说明均保留在上文。

以前的组织演示主要按提前写好的规则决定何时组队。要研究长任务中是否需要调整团队，首先得知道运行中发生了什么、任务需求有没有变化，再考虑组织方案。今天先补齐这条观察和分析链路。当前研究准备围绕一张可调整的组织图 `G_t` 展开，任务需求和信息来源先用记录维护；没有把旧的三图示意做成已实现的算法。

### 2. P1 完成了什么

**先把已经发生的事情记清楚。** 今天补齐了已有观察记录：可以保存已收到的用户任务和环境通知、工具动作与成功返回的结果，以及执行实例身份、可取得的时间和部分模型输入信息。同一事件可以保留稳定编号，之后能追查判断依据。它只记录已经发生的事情，不读取未来通知或任务答案（[online_observation.py](../../security_adaptive_mas/online_observation.py)）。目前 Bridge 只接上了成功工具返回；拿不到的 call_id 等字段仍留空，不能据此声称完整记录了所有失败和重试。

**让任务清单可以随着新消息更新。** 长任务执行到一半，可能又收到新要求或发现缺少材料，开始时的一次分析不够用。现在可以按固定任务 ID 新增或更新待办，保留来源；需要理解新消息时，接口允许 DeepSeek Flash 提出子任务、先后依赖和信息需求，再由 Python 检查引用的证据是否已经到达、依赖是否有错误（[online_task.py](../../security_adaptive_mas/online_task.py)、[task_proposer.py](../../security_adaptive_mas/task_proposer.py)）。这只是准备好的任务分析接口，尚未在真实 ARE 运行中自动完成任务分解。证据存在也不等于模型理解正确，模型说“完成”只能记为建议。

**用便宜的判断先筛一遍。** 新增的轻量监测模块根据新任务、环境通知和工具结果，判断是否值得再分析。普通判断由 Python 完成，不需要每一步都调用 DeepSeek（[performance_monitor.py](../../security_adaptive_mas/performance_monitor.py)）。它给出三种结果：

- **KEEP**：暂时没有已验证的重分析触发，保持当前状态；不表示这个结果一定无关。
- **ANALYZE**：值得进一步理解，先记入待分析清单；不表示模型请求已经发出。
- **RECONSIDER**：任务需求结构有变化，值得之后比较组织方案；不表示应该立即重组，也不表示收益已经算出来。

四类性能信号的记录位置也已准备好，但目前能力不同：

| 信号 | 想了解什么 | 现在能做到什么 |
|---|---|---|
| P | 有多少工作适合并行 | 缺可靠时长和已知依赖，仍不能可靠估计，保留 UNKNOWN |
| D | 哪项工作还需要什么信息 | 可以保存具体需求、相关任务、证据及已知提供方；不知道提供方就留空 |
| C | 模型是否反复收到相同材料 | 只统计完全重复的整份模型输入字符数，不能当作重复 Token 或已节省的费用 |
| W | 团队是否在无效等待或交接 | 尚无真实多 Agent 等待数据；明确单实例时为“不适用”，其他情况未知 |

**把这些模块按顺序连起来。** 协调模块现在能接收事件，交给 Python 预筛，在调用方明确选择的时点请求任务提案，检查后再记录是否值得重新考虑组织。新入口采用 Shadow Mode，也就是只观察、记需求和提出建议，默认监测与任务 LLM 开关都关闭，还不会自动改变拓扑图（[controller.py](../../security_adaptive_mas/controller.py)）。额外任务分析和执行 Agent 使用同一运行预算，分析请求的重试也要计数，不能把 Controller 的模型成本漏算（[deepseek.py](../../security_adaptive_mas/deepseek.py)）。

### 3. P1.1 修复了什么

**第一处是保护用户原始任务。** 审查发现，模型以前可以用相同的 `root` ID 提交新描述，覆盖用户目标。这会混淆“外部材料说了什么”和“用户到底要求做什么”。现在普通提案一律不能修改 root，只有实际到达的 USER 消息能刷新它；后来真正新增的 USER 要求仍会纳入同一个根任务，原有实际状态不会被模型覆盖（[online_task.py](../../security_adaptive_mas/online_task.py)、[task_proposer.py](../../security_adaptive_mas/task_proposer.py)）。这项修订约束任务来源，没有证明系统已经能够识别所有错误理解或攻击。

**第二处是明确工具结果为何需要再分析。** 系统不能看见工具返回，就凭工具名或文字猜它属于哪项需求。今天留下了显式的一次性关联接口：受信任的执行调用方可以把已登记需求关联到下一次工具调用，调用前消费，错误或过期的关联报错，工具失败后不会遗留到下一次。没有明确关系时记录“未关联”，不会强挂到所有任务上；有关联也只表示值得分析，不表示需求已满足（[are_bridge.py](../../security_adaptive_mas/are_bridge.py)、[performance_monitor.py](../../security_adaptive_mas/performance_monitor.py)）。**目前没有可靠的自动关联调用方，尤其没有接上官方 default Agent 的任务上下文。**

为了让后续排查更容易，日志现在还区分“已收到事件”“待分析”“分析成功并给出合法建议”和“任务真实完成”。模型给出空提案时，可以记为已分析但仍缺证据，不能直接写成“不相关”（[controller.py](../../security_adaptive_mas/controller.py)）。

### 4. 现在整个系统能做到哪一步

在离线契约测试中，已经可以走完“事件到达 → Python 预筛 → 注入模型提案 → 校验并更新需求 → 记录判断”的链路。受限 Bridge 的通知和成功工具结果回调也已接入观察入口。但真正向 DeepSeek 请求任务分析仍需显式开启、共享预算并手动选择调用时点；本轮测试使用的是注入响应。

因此，当前交付的是可验证、可由调用方显式驱动的观察与建议接口。它还没有接入原来跑通五个 Case 的官方 default 路径，没有自动分配或启动新的团队，也没有真正执行动态 `G_t` 重组。

### 6. 仍然存在的问题

- 新 TaskProposer 尚未通过真实 DeepSeek API 验证，JSON 提案在真实接口上的兼容性仍待确认。
- 尚未确定 ARE 执行中哪个时刻适合自动调用任务分析；插入请求可能影响模拟时间和执行顺序。
- 缺少可信的子任务完成记录，不能可靠判断工作是否实际完成；旧 root 的完成状态也不能证明新增目标已完成。
- 工具结果与需求的自动关联仍缺可靠调用方，多实例和并发关联没有验证。
- P/D/C/W 尚未形成真实性能收益估计，不能据此宣称应该增加 Agent 或已经节省成本。
- 新 Controller 尚未接入原五例的官方 default Agent 路径。当前受限 Bridge 会改变工具集合，不能拿它冒充被动接入。
- 还没有真正的动态 `G_t` 组织执行，也没有加入攻击实验或验证安全收益。

### 7. 下一步工作计划

1. 先完成 P1.1 Review，核对用户目标保护、关联消费和状态记录是否符合预期。
2. 明确 ARE 的安全分析时点、工具结果的关联来源和任务完成事实来源，再考虑接入官方 default 的被动观察接口；不能因此改变原工具权限或执行行为。
3. 接口边界确定后，再经明确同意安排小规模真实 API 验证，并决定后续组织候选比较与执行工作。性能比较和安全实验另行制定条件与预算，不从现有 5/5 或离线测试推出收益结论。
